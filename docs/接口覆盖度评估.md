## 一、结论（相对 v1 的修正）

| 结论 | v1（纯文档推断） | v2（静态核验） |
| --- | --- | --- |

## 三、对 PRD 的 4 条硬修订

### 1. 删除 `crowdLevel`

PRD §6.2 的响应示例中每个 `upcoming[]` 都带 `crowdLevel`，但没有数据源。
建议直接删掉；若要保留「拥挤度」体验，只能基于历史客流自建估算并标注为估算值。

### 2. 修正 `isSpecial` 的字段名

文档写「跳过 `isSpecial()` 的站」，容易让人以为 JSON 里有个 `isSpecial` 字段。
实际是 **`stations[].special == 1`**，只有方法名叫 `isSpecial()`。

```json
{ "order": 25, "sId": "010-8017", "physicalStId": "...", "sn": "天安门东", "special": 0, "distanceToSp": 420 }
```

### 3. 站数起点不是 `order`，而是 `drawOrder`

`drawOrder` 不来自 JSON（只在 `Parcel` 里读写，供客户端内部改序），所以**服务端聚合时必须用 `order`**；
但要知道：App 在跳站、区间车等场景会改写 `drawOrder` 覆盖显示顺序。
只认 `order` 的实现在这类线路上会与官方 App 差 1 站——可接受的偏差，但要清楚它从哪来。

### 4. `leg` 的 ETA 要按 `order` 匹配，不能盲取 `travels[0]`

`StnStateEntity` 每个元素都带 `order`。§6 的「直接使用 `travels[0].travelTime`」只在单目标站请求下成立；
双程联程需要**每辆车对目标站**的 ETA，必须：

```js
const hit = bus.travels.find(t => t.order === targetOrder) || bus.travels[0];
```

否则当 `travels` 同时返回后续多站预测时，会取到「下一站」而不是「你的目标站」。

## 四、仍需真机确认的 2 件事

> 2026-11-27 已在真机（小米 14 / Android 16 / HyperOS 3.0 / 车来了 7.6.9）上跑过一轮，
> 原第 3 项「线路关键词检索」已闭环：搜索 `302` 命中线路组 `302路 / S302路 / 3025路` + 目的地 POI。

1. **最小必填参数集**：只传 `lineId + targetOrder + stationId` 能否刷新（App 恒发全量：`lineId/lineNo/lineName/direction/physicalStId/filter/lng/lat/gpstype/isNewLineDetail/cryptoSign`）。
2. **`travels` 实际长度与覆盖范围**：只有目标站 1 条，还是目标站之后全部站点。
   —— 这两项都需要一次带签名的真实请求，App 界面无法反推。

## 五、两个必须由产品决策的风险（未变）

### 1. 轮询节奏：10s 是官方建议的 3 倍

`maxInterval=30`、`refreshInterval=0`。双程 10s 轮询 = 12 次/分钟/用户；即使服务端 10s 缓存去重，上游仍是 6 次/分钟/线路。

建议：**恒定 30s 轮询 + 本地按秒外推**（拿到 `travelTime` 后自行递减渲染，30s 校准一次），
仅当 `≤1 站 且 ≤120s` 时允许少量 10s 补拉（单次追踪上限 6 次）。既有秒级观感，又不突破上游节奏。

### 2. 密钥与合规

签名/解密依赖 `AKey.KEY`、`3DES_KEY`、`CRYPTO_OFFSET`（均在 APK 内）。
**本次评估只做「结构可复现」，不把密钥落进任何交付物**：这是非公开接口，
公开发布需评估服务条款；本地使用也应保持低频。

## 六、新增：环线风险

`LineEntity.loopMidStopName` 说明存在环形线路。环线 `order` 不满足「上车站序号 < 下车站序号」，
而 PRD 与当前实现都假设了两者单调递增。

处理建议（择一）：
- 规划页对环线改用「沿行驶方向的站序偏移」判断，而非简单比大小；
- 或首版直接不支持环线：`loopMidStopName != null` 的线路在 Builder 里置灰并说明原因。

## 七、真机实测（2026-11-27 · 小米 14）

环境：`23127PN0CC` / Android 16 / HyperOS 3.0（V816）/ 车来了 7.6.9（437），与 APK、文档完全一致。
方式：`adb connect` 无线调试 + `uiautomator dump` 取控件坐标 + 逐步截图核对。
（真机截图未入库，结论以本节文字记录为准。）

### 1. 数据契约在 UI 上得到印证

线路详情页展示 `14 分钟 / 4 站 / 5.0 千米`；
点「更多车辆」后单车条目为：

```
编号 新AB0397
14分钟·4站·2.1千米     12:02到达
下一站 新洲城市花园
```

→ 一次响应里同时具备：`etaMinutes` / `stopsLeft` / `distanceMeters` / `arrivalTime` / `nextStationName`。
**PRD 需要的能力全部命中**，且 `nextStationName` 可直接用，不必自己反查站名。

### 2. 「最近 3 辆车」的假设不成立

该线路在途**只有 1 辆**，「更多车辆」页只有 1 条记录，底部提示「更多班次信息可参考发车时间」。

→ 小部件/候车页必须能优雅降级到 1–2 辆：不要写「最近 3 辆」的固定标题和固定三行布局。
建议文案改为「在途车辆」（有 1 辆就显示 1 辆）。

### 3. 线路号检索可用

搜索 `302` 命中线路组：`302路 / S302路 / 3025路`，另有「目的地」POI 组。

→ 规划页可以做「输入线路号直接选线」，不必强制走「选城市 → 翻列表」。

### 4. 站点维度还有两个可用字段

站点列表里每个站名下方带地铁线标签（`1号线` / `2号线`），当前等车站带「离我最近」徽标
→ 对应 `StationEntity.metros`；「离我最近」即 `targetOrder` 的来源。

### 5. 全流程没有拥挤度

首页、详情、更多车辆、搜索四个页面均无「拥挤 / 舒适」文案 → 与静态分析完全一致，`crowdLevel` 必须删。

### 6. 差异化定位成立

「路线规划」是「起点 → 终点」的一次性方案（地图 + 步行/骑行/公交），不做双程实时同屏，也不评估「能否赶上」。
→ PRD 的核心差异化（联程同屏 + 换乘可行性徽章）确实没人做，值得做。

### 7. 两个与 PRD 不一致的事实

- **超级岛在 HyperOS 3.0 上已存在**（状态栏可见音乐 + 应用双岛）。PRD 写「HyperOS 4 专属」，
  但实际 OS3 就能开发联调，不必等 OS4。
- **广告密度很高**：开屏广告、信息流卡片、「干饭福利」、右下角意见反馈浮窗。
  PRD 的「零广告极简」不是空想，是真实痛点；但也说明这类工具的商业化路径很窄。
